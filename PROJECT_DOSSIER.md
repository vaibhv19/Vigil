# Vigil: Autonomous Agent Evaluation Harness & Safe-Runtime Sandbox

## 1. Project Overview

**Vigil** is a deterministic evaluation harness and safe-runtime execution sandbox designed to benchmark, evaluate, and test autonomous AI coding and reasoning agents. Built in Python 3.12+ (with Python 3.14 support), Vigil evaluates agents based on the **physical side effects** of their actions—inspecting files created, shell commands executed, process exit codes, and stdout/stderr streams—rather than relying on subjective textual output.

Vigil provides an end-to-end evaluation pipeline:
- **Ephemeral Sandbox Engine**: Provisions isolated, resource-constrained Docker containers per task with non-root privileges, read-only root filesystems, and strict CPU/memory boundaries.
- **Interception & Safety Monitoring**: Intercepts shell and tool calls prior to container execution, enforcing step limits and scanning for path escapes and forbidden subprocesses.
- **Deterministic Assertion Engine**: Validates sandbox terminal state against 6 Pydantic-validated assertion types (`file_exists`, `file_content_match`, `exit_code`, `stdout_contains`, `tool_call_count`, `json_schema`).
- **Telemetry & Regression Analytics**: Persists detailed suite metadata, task outcomes, individual tool call traces, and anomaly incidents to PostgreSQL 16, calculating P50/P90 latency percentiles and version-over-version differential diffs.
- **Developer Interfaces**: Includes a Typer-powered CLI (`vigil status`, `vigil run`, `vigil bootstrap`), a FastAPI REST backend, and a zero-dependency vanilla JS/CSS dark-mode dashboard SPA.

---

## 2. Why I Built It

As autonomous AI agents (such as ReAct loops, coding assistants, and tool-using LLMs) increasingly generate and execute arbitrary code, evaluating their reliability and safety presents two critical problems:

1. **The Flaw of "LLM-as-a-Judge"**: Traditional evaluation frameworks evaluate agents by prompting another LLM to grade the agent's textual response. This approach is non-deterministic, expensive, prone to model bias and hallucinations, and fundamentally incapable of verifying whether generated code actually runs, satisfies schema requirements, or produces correct filesystem side effects.
2. **Host Vulnerability & State Bleed**: Executing untrusted agent commands directly on host developer machines poses severe security and environmental risks, including directory traversal, resource exhaustion, accidental file modification, and cross-task state leakage.

Vigil was built to establish an objective, reproducible, and safe evaluation standard: treating agents as untrusted software, executing their tools inside isolated ephemeral sandboxes, deterministically verifying their outcomes against state assertions, and tracking performance and safety regressions across agent iterations.

---

## 3. Problem / Question

1. **Deterministic Evaluation**: How can we objectively determine whether an autonomous agent successfully completed a software engineering task without trusting the agent's self-reported text or using a non-deterministic LLM judge?
2. **Safe Untrusted Execution**: How do we safely execute arbitrary shell commands generated by an LLM without exposing the host operating system, host environment variables, Docker socket, or neighboring task files?
3. **Agentic Failure Mode Interception**: How can we intercept and halt common agent-specific failure modes (infinite reasoning/tool loops, directory traversal escapes, and forbidden shell reconnaissance tools) before they execute inside the container?
4. **Regression Tracking & Observability**: How do we capture granular execution telemetry (every individual tool call, argument, latency, stdout/stderr, and exit code) and compare agent versions across latency percentiles (P50/P90), pass rates, and step efficiency?

## 4. What It Actually Does

- **Provisions Ephemeral Docker Sandboxes**: Launches a single isolated container per evaluation task from `vigil-sandbox-base:latest`, running as non-root `vigil-user` (UID 1000), capped at 512MB RAM and 0.5 CPU cores, with network disabled (`network_mode="none"`), root filesystem mounted read-only, capability dropping (`--cap-drop=ALL`), and `no-new-privileges=true`.
- **Mounts Isolated Host Workspaces**: Dynamically generates unique temporary host directories mounted to `/workspace` (the only writable directory) and injects predefined task seed files before container start.
- **Intercepts Tool Calls**: Routes agent commands through `VigilSandboxTool` to `ToolExecutor`, capturing millisecond execution durations, process exit codes, and stdout/stderr streams via `container.exec_run(demux=True)`.
- **Enforces Multi-Tier Timeouts**: Enforces individual tool execution timeouts (e.g., 30s) and overall task timeouts (e.g., 180s–300s) using dedicated monitoring threads (`TimeoutExecThread`, `TaskExecThread`) that forcefully kill the Docker container on timeout.
- **Monitors & Blocks Anomaly Patterns**:
  - **Loop Detection**: Halts execution when tool call counts reach the task's `max_steps`.
  - **Path Traversal Scanning**: Validates command arguments against directory traversal tokens (`..`) and absolute path escapes outside `/workspace` and allowed system binaries.
  - **Subprocess Scanning**: Halts forbidden binaries (`curl`, `nc`, `ssh`, `wget`, `netcat`, `nmap`) and shell control metacharacters (`|`, `;`, `&`, `$`, `` ` ``).
- **Scores Deterministic Assertions**: Inspects post-task container terminal state and cumulative tool logs against 6 Pydantic assertion models:
  - `FileExistsAssertion`: Verifies target file creation.
  - `FileContentMatchAssertion`: Exact string or regex pattern matching within files.
  - `ExitCodeAssertion`: Validates final tool call exit code (e.g., `0`).
  - `StdoutContainsAssertion`: Substring or regex matching across cumulative stdout.
  - `ToolCallCountAssertion`: Verifies completion within $\le N$ steps.
  - `JsonSchemaAssertion`: Validates generated JSON files against JSON schema definitions.
- **Runs Parallel Task Suites**: Concurrently runs suites of YAML task definitions with bounded multi-threading (1 to 5 worker threads).
- **Persists Telemetry to PostgreSQL**: Records suite metadata (`eval_suites`), run parameters (`eval_runs`), individual task outcomes (`task_results`), tool call logs (`tool_calls`), and flagged violations (`anomalies`).
- **Computes Metrics & Comparisons**: Aggregates run statistics, calculates P50 and P90 latency percentiles via linear interpolation (`PercentileCalculator`), and performs side-by-side run comparisons (`RunComparator`) detailing task-level regressions (`PASS -> FAIL`), improvements (`FAIL -> PASS`), latency deltas, and step deltas.
- **Exposes REST API & Dashboard**: Provides FastAPI endpoints (`/api/runs`, `/api/runs/{id}`, `/api/metrics/runs/{id}/summary`, `/api/metrics/compare`) and serves a dark-mode Single-Page Application (SPA) dashboard.
- **Provides CLI Diagnostics**: Features Typer commands for environment bootstrapping (`vigil bootstrap`), system status checks (`vigil status`), and suite execution (`vigil run`).

## 6. Important Technical Decisions

1. **One Ephemeral Container per Task (Not per Tool Call)**:
   - *Decision*: Spin up a single container per task, execute multiple sequential tool calls inside it via `container.exec_run()`, and destroy it upon task completion.
   - *Rationale*: Spinning up a new container per tool call adds 1–3 seconds of latency per step and wipes out intermediate `/workspace` state (e.g. virtualenvs, installed packages, compiled binaries). Maintaining one container per task preserves local state while destroying it between tasks completely prevents cross-task state bleed.
2. **Deterministic Sandbox State Assertions over LLM-as-a-Judge**:
   - *Decision*: Score tasks purely on verifiable side effects (files created, content matches, process exit codes, stdout strings, schema validation).
   - *Rationale*: Eliminates the non-determinism, API cost, prompt sensitivity, and hallucination vulnerabilities inherent in LLM-based evaluation graders.
3. **Pre-Execution Anomaly Interception over Post-Execution Detection**:
   - *Decision*: Validate command strings and path arguments *before* issuing `exec_run` to Docker.
   - *Rationale*: Prevents dangerous commands (e.g. attempting to read host files or spawn unapproved network binaries) from executing inside the container, maps violations to structured failure taxonomy (`LOOP_DETECTED`, `PATH_VIOLATION`, `PROCESS_VIOLATION`), and immediately persists anomaly incident records.
4. **Physical Defense-in-Depth Isolation**:
   - *Decision*: Layer application-level validation on top of OS/container physical isolation (read-only root filesystem, unprivileged user UID 1000, network disabled, `--cap-drop=ALL`, `--security-opt=no-new-privileges`, 512MB RAM cap, 0.5 CPU cap).
   - *Rationale*: If an agent bypasses string validation via shell obfuscation, Docker's kernel-level namespace and cgroup limits prevent host tampering, network egress, or container root persistence.
5. **Multi-Tiered Container Cleanup Guarantee**:
   - *Decision*: Implement a three-tiered cleanup architecture: `try/finally` context managers for normal/timeout termination, an in-memory `ActiveContainerRegistry` hooked to Python `signal` handlers (`SIGINT`, `SIGTERM`) for process interruption, and Docker labels (`vigil-sandbox=true`) for manual sweep.
   - *Rationale*: Prevents "zombie container" resource exhaustion on developer workstations during aborted runs or IDE interruptions.
6. **Pluggable Agent Adapter Architecture**:
   - *Decision*: Isolate the agent framework (LangGraph) behind `BaseAgentAdapter` rather than coupling the evaluation engine to a single framework.
   - *Rationale*: Allows evaluating agents built on CrewAI, AutoGen, raw OpenAI tool-calling loops, or custom ReAct implementations without modifying the harness core.
7. **Strict Database Persistence (Fail-Hard on DB Outage)**:
   - *Decision*: Hard-fail with `DatabasePersistenceError` and abort evaluation if PostgreSQL operations fail, rather than silently falling back to unindexed local files.
   - *Rationale*: Guarantees telemetry integrity and prevents silent data loss during suite runs.

## 7. Interesting Engineering Problems

1. **Guaranteed Container Teardown During Abrupt Process Termination**:
   - *Problem*: Standard Python `finally` blocks do not execute if a process is terminated via SIGINT (Ctrl+C) or SIGTERM, leaving orphan Docker containers holding system resources and file locks.
   - *Solution*: Built an `ActiveContainerRegistry` class with thread-safe tracking (`threading.Lock`) that registers container IDs upon creation. Registered process-level signal handlers (`signal.signal`) that intercept termination signals, iterate over the active registry, issue forceful Docker `kill` and `remove` commands, and unregister containers before exiting with status `128 + signum`.
2. **WSL2 / Docker Desktop Memory Overcommit Nuances**:
   - *Problem*: On Windows hosts with Docker Desktop using WSL2, exceeding container memory limits (`mem_limit="512m"`) does not always trigger immediate OOM kill (exit code 137) if WSL2 dynamically allocates swap space from host RAM.
   - *Solution*: Documented the WSL2 kernel swap overcommit behavior in architecture specs and designed integration test suites to assert against both standard OOM termination and swap survival without false positive test failures.
3. **Linear-Interpolation Percentile Calculations**:
   - *Problem*: Python standard libraries do not provide a lightweight method for calculating continuous percentiles (P50, P90) from duration arrays without requiring heavy numerical libraries like NumPy or SciPy.
   - *Solution*: Implemented pure-Python rank calculation (`PercentileCalculator.percentile`) using Excel's `PERCENTILE.INC` standard (rank $r = \frac{p}{100}(n-1)$ with fractional linear interpolation between upper and lower indices), providing accurate percentile extraction across tool latency distributions.
4. **LangGraph Graph Recursion Bridging into Sandbox Tooling**:
   - *Problem*: LangGraph executes autonomous agent graph cycles where each node transition counts toward a recursion limit, making tool step enforcement tricky.
   - *Solution*: Created a custom LangChain `BaseTool` subclass (`VigilSandboxTool`) routing directly into the `ToolExecutor`, and dynamically calibrated the graph recursion limit to `max_steps * 2 + 2` to accommodate agent reasoning-to-tool-execution transitions while catching infinite loops via `GraphRecursionError`.

## 8. Failure Modes / Things That Went Wrong

1. **Infinite Agent Reasoning / Tool Loops**:
   - *Failure Mode*: LLMs generating repetitive tool calls in cyclic loops, exhausting tokens and CPU.
   - *Mitigation*: Intercepted at two layers: `AnomalyDetector` triggers an `AnomalyException` (pattern `LOOP`, severity `CRITICAL`) when `current_calls >= max_steps`, and `LangGraphAgentAdapter` enforces graph recursion limits.
2. **Directory Traversal & Filesystem Tampering**:
   - *Failure Mode*: Agents attempting relative directory escapes (`../../etc/passwd`) or absolute paths (`/var/run/docker.sock`).
   - *Mitigation*: Pre-execution `PathValidationLayer` flags `..` tokens and non-whitelisted absolute paths as `PATH` anomalies; Docker's read-only root mount physically blocks any write attempt outside `/workspace`.
3. **Subprocess Network / Reconnaissance Probing**:
   - *Failure Mode*: Agents running unauthorized networking binaries (`curl`, `nc`, `ssh`, `nmap`) or chaining commands via shell metacharacters (`|`, `;`, `&`).
   - *Mitigation*: `SubprocessAllowListScanner` scans command argument arrays using word-boundary regex patterns, terminating execution before `exec_run`.
4. **Tool & Task Execution Hangs**:
   - *Failure Mode*: Agent commands hanging indefinitely on blocking I/O (e.g. `sleep 1000`).
   - *Mitigation*: Dual-thread timeout guards (`TimeoutExecThread` for 30s tool timeouts, `TaskExecThread` for 180s–300s task timeouts) that forcefully kill the container and raise `ToolTimeout` / `TaskTimeout`.
5. **Database Transaction Rollback on Mid-Suite Crashes**:
   - *Failure Mode*: Harness or agent crashing midway through a multi-task suite, leaving partial or corrupted database records.
   - *Mitigation*: Separated `eval_runs` from `task_results` and `tool_calls`. When an individual task completes or fails, its `task_results`, `tool_calls`, and `anomalies` records are immediately committed inside atomic session context blocks (`get_session()`), ensuring that completed tasks remain intact if a subsequent task crashes.

## 11. What I Learned

1. **Observability Beats LLM Judgment**: Deterministically verifying an agent's physical side effects (filesystem diffs, stdout, exit codes, schemas) provides far more reproducible and actionable signal than asking an LLM to evaluate text.
2. **Multi-Layered Security is Mandatory for Code-Executing Agents**: String validation alone is insufficient for shell commands; physical OS constraints (cgroups, namespaces, read-only root, unprivileged users) must be paired with application-level interception to create safe evaluation boundaries.
3. **Robust Cleanup Requires Low-Level OS Hooks**: Simple context managers (`try/finally`) fail during abrupt process aborts; tracking active container handles in memory and binding to OS signal handlers is essential to avoid resource leaks.
4. **Adapter Decoupling Preserves Longevity**: Isolating agent framework abstractions (e.g., LangGraph) from the core sandbox and evaluation harness ensures the testing infrastructure outlives rapid churn in the agent ecosystem.

## 12. What Changed in My Thinking

- **From Subjective to Deterministic Evaluation**: Shifted from treating agent outputs as prose to be graded to treating agent executions as software integration test suites asserting against terminal state.
- **Honest Safety Boundaries**: Replaced vague notions of "AI safety" with concrete, well-defined infrastructure guardrails: bounding execution loops, restricting filesystem paths, preventing unauthorized binary execution, and enforcing resource limits.
- **Full Trace Durability**: Recognized that capturing the complete chronological trace of tool calls, inputs, outputs, and latencies is critical for understanding *why* an agent failed or regressed, not just *that* it failed.

## 13. Distinctive / Interesting Details

- **Discriminated Union Assertion Modeling**: Uses Pydantic v2 `Annotated[Union[...], Field(discriminator="type")]` for strict schema validation of evaluation definitions before execution.
- **In-Memory Active Container Registry**: Tracks live Docker container IDs across threads to ensure instant emergency teardown on `SIGINT`/`SIGTERM`.
- **Pure-Python Percentile Interpolation**: Implements Excel-standard `PERCENTILE.INC` (C=1 rank interpolation) without heavy external math dependencies.
- **Zero-Dependency SPA Dashboard**: Built with Vanilla JS and CSS tokens (custom properties, glassmorphism, responsive grid, live comparison diffs) served directly by FastAPI without node build pipelines.
- **Thread-Bounded Parallel Suite Runner**: Concurrently executes suites using `ThreadPoolExecutor` capped at 5 workers as specified by PRD requirements, preserving deterministic ordering in reports.

### LinkedIn Project Description
When evaluating autonomous AI coding agents, the standard approach is "LLM-as-a-judge"—asking another language model whether the output looks correct. But LLMs hallucinate, and textual answers can't verify whether generated code actually executes, respects schema boundaries, or creates the right filesystem state.

To solve this, I built **Vigil**: an autonomous agent evaluation harness and safe-runtime sandbox that benchmarks AI agents by observing their physical side effects rather than their textual answers.

Vigil spins up ephemeral, resource-constrained Docker containers per task (non-root `vigil-user`, read-only root, 512MB RAM, 0.5 CPU, network-isolated). Agent tool calls are intercepted before container execution, checking for infinite loops, directory traversal escapes, and unauthorized subprocesses. The harness scores task outcomes against 6 deterministic assertion models (files created, regex content matching, process exit codes, stdout captures, and JSON schemas).

All telemetry—every tool call, stdout/stderr stream, latency, and flagged anomaly—is persisted to PostgreSQL. A metrics engine computes P50/P90 latency distributions and differential comparisons across agent versions to detect regressions. The project includes a Typer CLI, a FastAPI REST API, and a dark-mode dashboard SPA.

Building Vigil reinforced a core engineering lesson: true reliability in autonomous systems comes from physical isolation, deterministic state verification, and granular execution telemetry.
